# Project Registry (Phase 07)

**Status:** implemented (`src/siamang/projects/`, `src/siamang/storage/projects.py`,
schema step v2). Runtime is still stdlib-only.

The Project Registry is SIAMANG's authoritative record of **which engineering
projects exist**: their stable identity, descriptive metadata, location, and
lifecycle. It is a small, synchronous, persistent component.

> **Project Registry does not manage Git.**
> **Project Registry does not manage tasks.**
> **Project Registry does not invoke models.**
> **Project Registry does not execute tools.**
> It also emits no events and adds nothing to contract v0.1.

## 1. Project identity

* `project_id` = `prj_<ULID>`, generated by `siamang.ids.new_id("project")`,
  the same `<prefix>_<ULID>` convention as `evt_`/`req_`/`tsk_`/`apr_`/`mrq_`.
  The contract's own example (`prj_example`) uses the same prefix.
* It is the **only** identity. Name, root path, type, description, and
  metadata can all change; the ID never does. The database enforces this: a
  trigger rejects `UPDATE` of `project_id` or `created_at`.
* An explicit ID may be supplied at registration (it must match
  `prj_[A-Za-z0-9][A-Za-z0-9_.:-]{0,123}`). Otherwise one is generated.

## 2. Definition

`Project` (frozen dataclass, `projects/definition.py`):

| Field | Type | Rules |
|---|---|---|
| `project_id` | `str` | see §1 |
| `name` | `str` | 1–100 chars, whitespace collapsed, no control characters |
| `description` | `str` | ≤ 2000 chars, newlines/tabs allowed, trimmed |
| `project_type` | `ProjectType` | `software`, `web`, `mobile`, `desktop`, `game`, `research`, `data`, `education`, `other` (default `other`) |
| `status` | `ProjectStatus` | `active`, `archived` |
| `root_path` | `str` | §4 |
| `metadata` | read-only mapping | §5 |
| `created_at`, `updated_at` | `datetime` (UTC) | stored as ISO-8601 `Z` strings, same helpers as Phase 3/05 |

`project_type` is **descriptive only**. It does not choose an agent, model,
tool set, or Git workflow. No speculative fields (branch, commit, owner,
model, agent, task) were added. Those belong to later phases.

## 3. Lifecycle

```
register ──► active ──archive──► archived
                ▲                    │
                └──────restore───────┘
```

* `archive` / `restore` are idempotent: archiving an archived project (or
  restoring an active one) changes nothing, including `updated_at`.
* **Archived projects are read-only.** `update` raises
  `ProjectArchivedError`; restore first.
* `restore` fails with `DuplicateProjectError` if an active project now
  holds the same name or root path.
* **No delete.** Project identity is durable (tasks and events will
  reference it), so there is no delete API and a trigger rejects SQL
  `DELETE`. Archive is the way to retire a project.
* Task/agent states (`running`, `failed`, …) are deliberately absent.

## 4. Root path semantics

Decision: **`root_path` is required, but the directory does not have to
exist.**

* **Required:** every project has a location reference, and Phase 08
  needs one.
* **Existence optional:** a project may be registered before it is created
  (for example by a future generator). `register(..., check_exists=True)`
  (the CLI default; disable with `--allow-missing`) performs **one**
  `isdir` stat call.

Normalization is pure string work. It never touches the filesystem and never
resolves symlinks:

* The path must be absolute POSIX. `~` and relative paths are rejected by the
  registry. The CLI expands them before calling the registry, so the stored
  value never depends on the working directory.
* `os.path.normpath` is applied: `.`/`..`/duplicate and trailing slashes are
  removed, and a leading `//` is collapsed.
* The following are rejected: control characters (including NUL and
  newline), more than 4096 chars, the filesystem root `/`, and the home
  directory itself (too broad to be one project).
* Two spellings that normalize to the same string are the same path.
  Symlinked aliases are **not** detected; Phase 08 decides whether
  repository identity matters.

The registry stores the location. It never lists, reads, scans, or runs
anything inside it.

## 5. Metadata

A JSON object for descriptive data, for example
`{"language": "python", "framework": "fastapi", "domain": "education"}`.

* **JSON only:** objects, arrays, strings, integers, finite floats,
  booleans, null. It is stored as canonical JSON (sorted keys, compact), and
  the database checks `json_valid` and that it is an object.
* **Bounded:** ≤ 64 top-level keys, ≤ 5 levels deep, ≤ 16 KiB serialized.
  Keys match `[A-Za-z][A-Za-z0-9_.-]{0,63}`.
* **Non-executable:** top-level keys that read as executable configuration
  (`command(s)`, `script(s)`, `exec`, `shell`, `run`, `hook(s)`,
  `entrypoint`) are refused. This is a guard, not a sandbox. The rule is
  that **no SIAMANG component ever interprets metadata as instructions**.
* **No credentials:** keys that look like credentials (`api_key`,
  `auth_token`, `password`, `secret`, …) are refused at any depth.
* `update(metadata=...)` **replaces** the whole object; there is no merge.
* Metadata does not affect routing, permissions, or anything else in this
  phase.

## 6. Duplicate rules

| Situation | Behavior |
|---|---|
| Same `project_id` | `DuplicateProjectError(field="project_id")` |
| Same name as an **active** project (case-insensitive via `casefold`, whitespace-collapsed) | `DuplicateProjectError(field="name")` |
| Same normalized `root_path` as an **active** project | `DuplicateProjectError(field="root_path")` |
| Name/path of an **archived** project | Allowed: a new active project with a new ID. The archived one keeps its values as history |
| Restore while an active project holds the name/path | `DuplicateProjectError`; stays archived |
| Renaming a project to a different case of its own name | Allowed (no conflict with itself) |
| Unknown project | `ProjectNotFoundError` (also a `LookupError`) |
| Invalid field | `InvalidProjectError(field=...)` (also a `ValueError`); nothing written |
| Update to archived project | `ProjectArchivedError` |

The rules are checked inside the write transaction **and** backed by partial
unique indexes (`WHERE status = 'active'`), so they hold even if the Python
checks were bypassed. Error messages name the conflicting project ID but
never include paths or metadata.

Names are not identity. They exist for humans and for later hint resolution:
contract `task.request.project.hint` → `PROJECT_NOT_FOUND` /
`PROJECT_AMBIGUOUS` is Task Engine work (Phase 10). `get_by_name` is exact
after normalization, not fuzzy.

## 7. Persistence

* The existing `Database` (Phase 3/05) is reused. The schema went from v1 to
  **v2** via an ordered step list (`SCHEMA_STEPS = ("schema.sql",
  "schema_v2.sql")`).
  * A fresh database runs both steps.
  * An existing v1 database runs only step 2, in one transaction, with its
    tasks and events preserved.
  * A failed step rolls back and leaves the database at v1.
  * Applied steps are never edited. This is not a migration framework, just
    numbered SQL files.
* Layering: `ProjectRegistry` (rules, validation, transactions) →
  `ProjectStore` (SQL only, plain `ProjectRow` strings, imports nothing from
  the domain) → SQLite.
* Every write runs as one `BEGIN IMMEDIATE` transaction: validate, check
  conflicts, write, commit. Any exception rolls back, so no partial project
  is stored.
* Every real change sets `updated_at`, never earlier than the previous value
  (clock-skew safe). `created_at` never changes. No-op writes write nothing.
* `tasks.project_id` remains a free text reference with **no foreign key**.
  Adding one would require rebuilding `tasks`, and existing tasks may name
  unregistered projects. The Task Engine (Phase 10) validates task → project
  through the registry.

### Table `projects` (STRICT)

`project_id` PK (`GLOB 'prj_?*'`), `name` (trimmed, 1–100), `name_key`,
`description` (≤ 2000), `project_type` (CHECK enum), `status` (CHECK
`active`/`archived`), `root_path` (absolute, ≤ 4096), `metadata` (CHECK
`json_valid` AND object), `created_at`, `updated_at`.

Indexes: `projects_active_name` (UNIQUE `name_key` WHERE active),
`projects_active_root` (UNIQUE `root_path` WHERE active), `projects_status`.
Triggers: `projects_no_delete`, `projects_immutable_identity`.

## 8. API

```python
from siamang.projects import ProjectRegistry
reg = ProjectRegistry(db)                       # db: siamang.storage.Database
p = reg.register(name=..., root_path=..., project_type="web", description="", metadata={}, check_exists=False)
reg.get(project_id) / reg.exists(project_id)
reg.get_by_name(name)                           # active only
reg.find_by_root_path(path)                     # active only, or None
reg.list(status=None, project_type=None)        # sorted by name, then id
reg.update(project_id, name=..., description=..., project_type=..., root_path=..., metadata=...)
reg.archive(project_id) / reg.restore(project_id)
```

## 9. CLI

```
siamang projects [list] [--all | --status S] [--type T] [--json]
siamang projects get <project_id> [--json]
siamang projects register --name N --path P [--type T] [--description D]
                          [--meta K=V ... | --metadata-json JSON] [--allow-missing] [--json]
siamang projects update <project_id> [same field flags] [--json]
siamang projects archive|restore <project_id> [--json]
```

* Read commands never create the database.
* `--json` prints one JSON value on stdout. Logs go to stderr.
* Errors print `error: ...` to stderr and exit 1; usage errors exit 2.
* Nothing runs Git, a model, the network, or reads inside the project.

Projects are never discovered or imported automatically. Register each one
with `siamang projects register`.

## 10. Security boundary

The registry never: spawns processes, runs Git, opens network connections,
reads environment variables or credentials, reads `.env` or any file inside a
project, lists or scans directories, resolves symlinks, or logs root paths
(log lines carry only the project ID and type/changed field names). Path
values are data and are never passed to a shell.

Enforced by `test_projects_security.py` and `test_projects_architecture.py`:

* Process and directory-listing functions are patched to fail, and any open
  under the project directory fails. The full registry and CLI lifecycle
  still works.
* A `.env` secret never reaches logs, CLI output, or the database file.
* Shell metacharacters in names and paths are inert.
* AST checks forbid `subprocess`, `socket`, `http`, `urllib`, `shutil`,
  `glob`, `asyncio`, Git/vendor modules, and `environ`/`getenv`/`listdir`/
  `scandir`/`walk`/`exec`/`eval`.
* The dependency direction is checked: storage never imports the domain, and
  only the CLI imports the registry.
* Mutation checks (adding `os.listdir` or reading `.env` in the registry)
  make the security tests fail.

## 11. Relationship with Phase 08 (Git Workspace Manager)

```
Project Registry ──(project_id, root_path, metadata)──► Git Workspace Manager ──► Git
```

Phase 08 reads a project from the registry and owns everything about the
repository: whether `root_path` is a Git repository, remotes, branches,
worktrees, status, diff, commits, and workspace preparation. The registry
will never call it.

Open questions handed to Phase 08 (answered in
[GIT_WORKSPACE.md](GIT_WORKSPACE.md) §5 and §8: nested roots and symlink
aliases are allowed and reported; §6 is enforced per repository, so a project
that is its own repository is allowed):

* Overlapping (nested) active roots are currently allowed. Should Phase 08
  forbid them?
* Symlink aliases of the same directory.
